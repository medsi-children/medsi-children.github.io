# REPORTS → список родителей: повторная синхронизация

Обновлено 21.10.2026. Код: `apps-script/medsi-bot/chat-d1-migration.js`.

- `onReportsD1Edit` / `onReportsD1Change` перед попыткой взять ScriptLock
  сохраняют новый непрозрачный токен `REPORTS_D1_SYNC_REQUEST`.
- При занятом lock запрос остаётся в Script Properties. Успешный проход
  записывает обработанный токен в `REPORTS_D1_SYNC_COMPLETED`. Раздельные
  request/ack не позволяют позднему завершению стереть более новое изменение.
- `retryPendingReportsD1ProfileSync` запускается раз в минуту; при совпадении
  токенов сразу выходит без Sheets/D1-запросов и обработки отчётов.
- Полный `syncD1ProfilesFromReports` остаётся раз в 10 минут: проверяет также
  регистрации и восстанавливает отсутствующие триггеры. Он автоматически
  устанавливает минутный retry после выпуска нового исходника; ручной запуск
  установщика не нужен. До первого такого прохода действует старое расписание.
- D1-профили обновляются/закрываются перед обработкой сырых отчётов и S3.
  Удаление по-прежнему ограничено тремя контактами за проход, с повторной
  защитной проверкой REPORTS и регистрационной очереди. Остаток сохраняет retry.
- Предыдущий снимок имён не заменяется до успешной обработки отчётов;
  ошибка или прерванный проход оставляет его для повторной обработки.
- Ошибки и незавершённая очистка не подтверждают запрос. Повтор безопасен
  благодаря существующей очереди S3 и повторной проверке актуального REPORTS.
- Журнал lifecycle содержит только количества/состояния, без снимков профилей.

Обычно свободный обработчик обновляет список за текущий проход; при занятом
обработчике повтор начинается на ближайшем минутном тике после освобождения.
Это не жёсткая гарантия 60 секунд: Google может задержать триггер, внешние
сервисы могут быть недоступны. В браузере чаты дополнительно обновляются polling,
телефоны — при открытии раздела.

Проверки: `npm run verify`, включая сценарии busy lock, нового события во время
прохода, сетевого сбоя, ошибки maintenance, лимита удаления и установки таймера.
Факт публикации и установленного живого триггера проверять отдельно.
