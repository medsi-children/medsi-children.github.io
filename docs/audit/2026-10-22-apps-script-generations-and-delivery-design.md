# Apps Script: поколения, доставка отчётов и короткая фиксация

22.10.2026. Проектное решение Sol для этапа D в
[`apps-script-refactor-plan-2026-10-22.md`](../apps-script-refactor-plan-2026-10-22.md).
Это проектная спецификация. По решению пользователя `childAdmissionId` добавлен
в скрытый REPORTS!H; коммит `575a018` опубликован через существующий web app.
На момент проверки H1 ещё не создан фоновым запуском; реальные строки не читались.
D1 и реальные семьи не менялись.

## Вывод

Порядок передачи отчёта можно защитить монотонной ревизией и условной записью в
D1. Старую регистрацию можно защитить от позднего outbox по уже существующему
`attemptId`. До текущей локальной правки в системе не было общего идентификатора
поступления ребёнка: строки `REPORTS` описывают контакт взрослого и ребёнка,
`DATABASE` тоже не содержит уникального ID госпитализации, а Worker хранит
профили по телефону. Идентификаторы `REPORT_ADMISSION_<phone>` принадлежат
телефону, не ребёнку. ID в `REPORTS!H` следует текущим правилам сопоставления
и закрывает повторное поступление после удаления старых строк. Он не различает
двух одновременно активных полных тёзок, которых текущий ключ уже объединяет.

Рекомендуемый порядок: сначала добавить и проверить fencing по поколению
родительского профиля и ревизии отчёта; отдельно подготовить явный источник
`childAdmissionId` для группировки родственников. В локальном Apps Script он
теперь хранится в скрытом `REPORTS!H`; передача его через D1 и fencing поколений
профиля/ревизии остаются отдельной незавершённой задачей.
Сокращать блокировки разрешать лишь после того, как Worker принимает только
подтверждённое активное поколение и более новую ревизию.

## Что уже есть и чего не хватает

| Данные | Сейчас | Роль и ограничение |
|---|---|---|
| `attemptId` | Уникальный ID регистрации в `parent_registration_attempts` и outbox | Подходит как поколение жизни одного профиля взрослого; повтор той же попытки сохраняет ID. Не является ID ребёнка и не должен меняться при обычном входе. |
| `REPORT_ADMISSION_<phone>` | Apps Script Property, новый UUID при добавлении строки | Ограждает raw-owner для одного номера. Это полезный локальный fence, но для другого родителя того же ребёнка будет другое значение. |
| `REPORTS` A:G | Телефон, взрослый, ребёнок, фамилия, отчёты и статус родителя | В основных полях нет ID поступления; перестановка строк и повторное создание одинаковой строки неразличимы. |
| `chat_profiles` | Ключ `phone10`, имена/ребёнок/родство | Нет поколения регистрации или общего ID ребёнка. Устаревший reconcile может перезаписать профиль с тем же телефоном. |
| `report_current` | Ключ `(phone10, kind)`, текст, fingerprint `version`, время | Fingerprint обнаруживает изменение текста, но не задаёт порядок двух разных доставок. `updated_at` получателя — не ревизия источника. |
| `report_snapshots` | Телефон, вид, дата и текст | Не отделяет историю прежней госпитализации от новой с тем же телефоном. |

`appsscript.json` задаёт веб-приложению `USER_DEPLOYING`. Это означает, что
`UserLock` в веб-запросах привязан к пользователю, который развернул приложение;
`ScriptLock` общий для пользователей скрипта. Но исходники не доказывают, каким
аккаунтом фактически созданы все установленные триггеры. Перед заменой lock
нужно получить только метаданные триггеров (`handler`, источник, тип, владелец
исполнения), без содержимого таблицы и данных семей. Список ожидаемых обработчиков
по коду не является подтверждением реального инвентаря.

## Идентификаторы для целевой модели

1. **`profileGeneration` — срок жизни профиля конкретного взрослого.** Для новых
   регистраций равен неизменяемому `attemptId`. Повтор входа и выдача новой
   сессии его не меняют. Удаление и последующая новая регистрация создают новое
   поколение. Существующие активные профили связываются с их завершённой
   регистрацией; если связь не найдена, остаются в legacy-режиме. Эта метка
   нужна для fencing операций, но сама по себе не сбрасывает и не отзывает
   сохранённую сессию.
2. **`childAdmissionId` — срок жизни госпитализации ребёнка.** Один ID для всех
   взрослых одного ребёнка в одном поступлении; новый ID при новом поступлении,
   даже с теми же именем и телефоном. Сам UUID случаен и не выводится из имени,
   телефона или raw-заголовка. Для новых регистраций текущие правила личности
   используются только чтобы найти уже существующую строку ребёнка и разделить
   ID с его родственником.
   Хранить его в скрытой служебной колонке H листа REPORTS, рядом с текущими
   полями, а не в новом листе или Cloudflare. Apps Script заполняет одинаковый
   ID строкам, которые уже считаются одним ребёнком по текущему точному ключу
   `NAME_VARIANTS` + фамилия + гендерные признаки. Новый ID создаётся после
   удаления всех строк прежнего поступления. Это наследует действующее правило
   сопоставления; оно не умеет отличить двух одновременно поступивших детей с
   полностью одинаковыми данными, если таблица сейчас считает их одним ребёнком.
3. **`revision` — порядок версии отчёта от GAS.** Отдельный возрастающий целый
   счётчик для каждого вида отчёта, сохраняемый вместе с committed fingerprint.
   Увеличивается только если реально меняется опубликованный payload либо
   состав roster-проекции. Повтор одинакового payload сохраняет ту же ревизию.
   Публикация/`publicationId` остаётся отдельной сущностью: сортировка строк,
   обслуживание справочника и повторная доставка не создают нового события,
   уведомления или сброса прочитанности.

`profileGeneration`, `childAdmissionId`, `revision` и текущий `version` для
прочитанности имеют разные задачи и не подменяют друг друга.

## Протокол регистрации и удаления

- Worker остаётся первым владельцем регистрации и durable outbox. Каждая запись
  outbox несёт `attemptId` и ожидаемый `profileGeneration`.
- GAS под коротким `ScriptLock` подтверждает, что попытка всё ещё активна для
  этого поколения, затем проверяет и добавляет строку. Между этой проверкой и
  append нет внешнего HTTP-вызова.
- ACK Worker адресован парой `attemptId + profileGeneration`. Он удаляет только
  этот outbox и подтверждает успех, только если поколение всё ещё активно.
  Поздняя отмена не может быть переиграна ответом старой попытки. Простой GET
  перед append не является защитой: отмена всё ещё может случиться после GET.
- Если отмена произошла после append, но до ACK, GAS сохраняет факт применения
  этой попытки и сообщает Worker, что требуется компенсация/удаление именно этой
  проекции. Нельзя «успешно ACK-нуть» отменённую регистрацию или автоматически
  восстановить её следующим reconcile.
- Reconcile и перенос номера сравнивают ожидаемое и текущее поколения. Старый
  снимок не может создать/перезаписать профиль после выписки или re-admission.
  Неуверенное состояние останавливается с видимой ошибкой и повторяется по
  прежнему ID; оно не превращается в постоянный запрет входа.
- Очередь выписки получает поколение. Повтор завершённой старой операции остаётся
  идемпотентным; операция прежнего поколения не удаляет новую регистрацию того
  же телефона.

Для устойчивого `applied`-маркера предпочтительнее существующий Worker/D1, а не
новый рост Script Properties: Apps Script ограничивает значение свойства 9 KB,
общий размер хранилища 500 KB. Не помещать туда весь roster или тела отчётов.

## Протокол отчёта и истории

1. `load`: подготавливаются roster, raw-источник, NAME_VARIANTS и предыдущие
   значения. Сохраняются их fingerprints и поколение каждой строки.
2. `compute`: чистый расчёт строит payload, `publicationId` и целевые поколения;
   побочных эффектов нет.
3. `commit`: короткая общая секция проверяет, что raw и roster не изменились,
   адресно записывает E/F и фиксирует следующую `revision`/fingerprint. Перед
   освобождением lock изменения таблицы сбрасываются. При несовпадении снимка
   отложить повторный расчёт; не коммитить устаревший plan.
4. `deliver`: HTTP в Worker выполняется вне lock и несёт поколение, `revision`,
   `publicationId`, payload и fingerprint.
5. Worker принимает пакет только при активном поколении профиля. Для пары
   `(phone, kind, profileGeneration)` меньшая ревизия отклоняется; равная
   ревизия с тем же payload считается повтором; равная с другим payload —
   конфликт; большая ревизия принимается. Проверка активности поколения и UPSERT
   выполняются одной D1-операцией/пакетом без промежуточного окна.
6. `ACK`: GAS подтверждает локально только доставленную ревизию. Если за это
   время уже появилась более новая, ACK старой не очищает её запрос.
7. History capture использует те же поколение и исходную публикацию. Повтор
   capture того же `(admission, kind, date, publicationId)` идемпотентен.
   Запросы current/history и удаление профиля фильтруются по поколению; старое
   значение не оживляет доступ или отчёт новой регистрации.

Условный UPSERT должен запрещать update из stale-пакета даже тогда, когда он
пришёл физически позже. Сравнение `Date.now`, порядок HTTP-запросов и повторный
GET такую гарантию не дают. `read_version` остаётся отдельным состоянием: новую
ревизию без нового `publicationId` нельзя ошибочно выдавать за новый отчёт.

## Порядок реализации и выпуска

1. **Read-only техническая сверка:** фактические установленные GAS triggers,
   источник и аккаунт-владелец; реальные web app deployment metadata; доступные
   `attemptId` для активных профилей — только агрегированные counts/coverage.
   Ни телефоны, ни имена, ни строки отчётов не выгружать.
2. **Добавить схему совместимым расширением:** `profile_generation` для профиля,
   `child_admission_id` (пока nullable/legacy) для профильной связи, `revision` и
   поколение в current reports, поколение/публикацию в snapshots. Новую migration
   добавить отдельным файлом; сначала проверить её на локальном синтетическом D1.
   До миграции Worker код не может ссылаться на новые поля.
3. **Worker tolerant:** принимать старый формат в прежнем режиме, новый —
   проверять generation/revision. Задеплоить совместимый Worker после миграции.
4. **GAS writer:** передавать поколения, проверять cancel/attempt атомарно через
   условные Worker endpoints, добавить локальные checkpoint/ACK. Устанавливать
   Локальный `childAdmissionId` в `REPORTS!H` уже используется для raw-owner;
   передавать его D1 можно после расширения схемы и проверки Worker.
5. **Наблюдение без PII:** агрегатные счётчики старого/нового протокола,
   stale rejection, duplicate ACK, конфликт ревизий, retry и legacy coverage.
   Если есть необъяснимый legacy-поток, строгий режим не включать.
6. **Worker strict:** отвергать неизвестные поколения и старый пакет без
   `revision`; старые активные профили переводить в новую модель только после
   подтверждённого соответствия их текущей строки/регистрации. Сессии не сбрасывать.
7. **Короткие блокировки:** общий lock оставить только для локального
   validate/commit/ACK state. Worker, Contacts и S3 вызывать вне него. Долгие
   фоновые операции получают сохраняемую lease/claim; занятость означает очередь,
   а не ожидание интерфейса.
8. **Удаление legacy:** только после того, как старые запросы и профили имеют
   покрывающий migration path и нет активных потребителей. Trigger entry point
   не удалять, пока не подтверждены реальные установленные триггеры.

Каждый deployment-этап должен быть обратно совместим. Применение D1 migration,
переключение strict mode и изменение источника ID не объединять в одну
необратимую операцию. Схема не меняет возраст/срок сессий, passkey-поведение,
интерфейс входа, NAME_VARIANTS или правила разбора отчёта.

## Обязательные синтетические сценарии

- отмена регистрации до lock GAS, во время локальной проверки и после append до
  ACK; повтор старого ACK после новой регистрации;
- выписка и новая регистрация того же телефона/имени между fetch и apply;
- старый HTTP-пакет прибывает после новой ревизии и не меняет current/history;
- процесс падает после D1 apply до ACK, повтор того же revision не дублирует
  unread/push; равный revision с другим payload виден как конфликт;
- два родителя одного admission имеют разные profile generations, одинаковый
  childAdmissionId и получают один соответствующий отчёт;
- два одновременно активных ребёнка-тёзки имеют разные admission IDs и нигде
  не сливаются; отсутствие ID блокирует автоматическую догадку;
- повтор history capture, re-order строк, ручное изменение raw между compute и
  commit, параллельное удаление, пустые/отсутствующие отчёты;
- каждый сценарий запускается с синтетической D1 и заглушёнными внешними API.
  Никакие реальные дети, телефоны или сообщения не используются.

## Граница перед реализацией

Для текущего распределения Apps Script хранит `childAdmissionId` в
скрытом `REPORTS!H`; это локальная метка поступления, не D1 и не новая
авторизация. Она действует в пределах нынешнего ключа сопоставления ребёнка и
не различает одновременных полных тёзок, которых текущая логика уже объединяет.
Не считать индивидуальный `attemptId` или `REPORT_ADMISSION_<phone>` общим ID.

Проверенная конфигурация-манифест указывает `executeAs: USER_DEPLOYING`; установленные
trigger IDs/создатели фактически не запрашивались в этом проходе. Поэтому
области блокировок пока не менялись. Официальные определения:
[LockService](https://developers.google.com/apps-script/reference/lock/lock-service),
[web app executeAs](https://developers.google.com/apps-script/manifest/web-app-api-executable),
[Properties limits](https://developers.google.com/apps-script/guides/services/quotas).
