## Выполнено

  Обработка отчётов больше не дописывает начальную букву фамилии обратно в C;

- Перед заменой имени скрипт проверяет, что готовый заголовок всё ещё указывает
  на того же ребёнка. Если нейтральная форма «Саша» делает пару неоднозначной,
  сохраняется различающая исходная форма.

## Что хочет пользователь

В `REPORTS!C` хранить только имя: `Александр`, `Александра`, `Екатерина`.
В `REPORTS!D` — полную фамилию. Не дублировать начало фамилии в столбце имени.
В сыром отчёте бот использует предпочитаемую воспитателями форму имени из
первого столбца NAME_VARIANTS и добавляет однозначное уточнение фамилии.
Если имя отсутствует в словаре, сохраняется написанная воспитателем форма.
В родительском заголовке используется зарегистрированное имя из C. Это разные
правила отображения: Вова в raw может стать Володей только у родителя, если
такое имя сохранено при регистрации. Текст внутри предложений не заменяется.

Нужно пройти всю цепочку, включая Apps Script, Cloudflare, веб-интерфейс,
регистрацию и выписку. Задача не сводится к удалению букв из C.
Сначала устранить зависимости и обеспечить совместимость, затем очистить C
у действующих профилей и переключить новую регистрацию. Уже вошедшие родители
продолжают пользоваться ботом, текущие отчёты остаются доступны.

## Правила, которые нельзя менять заодно

- NAME_VARIANTS объединяет формы имён для сопоставления. Записанное родителями
  имя в C и родительском заголовке не переименовывается по словарю.
  Первый столбец получает отдельную роль предпочитаемой формы только для raw.
- Явные Александр/Александра различаются. Нейтральное Саша не доказывает пол.
- Одна семья может иметь несколько родительских строк. Они разделяют одно
  поступление, но не становятся одним телефонным профилем.
- Существующие H (ID поступления) и I (внутренняя метка регистрации) сохраняются.
  Не менять метки, токены, passkey, сроки сессий или правила входа ради имени.
- Новый ребёнок после выписки тёзки не получает старый ID и чужой отчёт.
  Два разных текущих ID не объединяются по похожим именам/фамилиям.
- DATABASE и Google Contacts нужны. Исторические записи не чистить массово.
- Событийная обработка и дневная страховка из `report-scheduler.js` сохраняются.
  Не возвращать полную пересборку каждую минуту или старую запись чатов в Sheets.
- Тела raw, распределённых и исторических отчётов не переписывать ради теста.
  Новую рассылку родителям не устраивать.

## 2. Целевая логика

Разделить три разных понятия:

1. **Сохранённое имя и полная фамилия:** C/D таблицы, понятный контракт в Cloudflare.
2. **Короткая подпись:** вычисляется для конкретного списка детей; не является ID.
3. **Поступление:** существующий H. Удаление инициала не создаёт новое поступление.

Если одна буква не различает детей, взять две, затем три/четыре или полную фамилию.
Не определять личность только по видимой подписи. Мама «Александра Баженова» и
папа «Саша Баженова» должны найти одного текущего ребёнка по правилам словаря и
полной фамилии, а не получить новое поступление из-за формы имени.

Отдельно проверить существующие ограничения: короткое уточнение сейчас ожидается
с заглавной буквы; фамильный префикс распознаётся длиной 2–4 буквы. Полная фамилия
может формироваться как запасная подпись — убедиться, что следующий разбор её
тоже понимает. Не расширять угадывание опечаток и неоднозначных имён заодно.

## 3. Совместимость существующих данных

До очистки C:

- Получить обратимую карту `телефон + H + старое C + D → новое C` вне Git.
  Сохранить только необходимые служебные состояния; не экспортировать все
  Script Properties с секретами. Сначала убедиться, что H у действующих строк
  корректны и не конфликтуют; не присваивать новые ID вслепую.
- На синтетической копии состояния проверить старые записи владения raw и
  текущие отчёты. Обеспечить переход со старого ключа на новый, подтверждая
  принадлежность тому же поступлению и контактам. Не очищать реестр владельцев.
- Если нужна временная совместимость старой/новой формы, сделать её узкой,
  с явным условием завершения и документированным удалением. Не оставлять
  бессрочный второй путь сопоставления и не восстанавливать старый вход.
- Удалять из C только распознанное уточнение фамилии, подтверждённое D.
  Составные имена и неизвестные значения не обрезать по последнему пробелу.
  Не менять форму имени по словарю: Катя остаётся Катей, Екатерина — Екатериной.

## 4. Выпуск по порядку

1. Обновить чтение/проверки так, чтобы старые и новые строки были безопасны.
   Проверить, какие компоненты должны выйти раньше остальных; зафиксировать это.
2. Опубликовать совместимые изменения Cloudflare/Apps Script/веба там, где они
   действительно нужны. Новое имя в C не должно застать старую несовместимую
   проверку владения. Изменения только документации не считать выпуском кода.
3. Переключить запись новых регистраций, чтобы они больше не добавляли инициал в C.
4. Однократно мигрировать существующий C по сохранённой карте. Каждую запись
   менять только если её телефон, H, D и прежнее C всё ещё совпадают с планом.
   При изменении строки пропустить её и построить актуальный план, не затирать.
   Состояние соответствия старой/новой записи закрепить в безопасном порядке
   до/вместе с очисткой C; этот промежуток тоже покрыть тестом сбоя.
5. Дать штатной синхронизации обновить представление в D1 и кэше, сохранив
   ID, сессии, сообщения, отчёты и прочитанность. Не запускать принудительные push.
6. Сверить необходимые агрегаты и принадлежность текущих отчётов; сравнить
   контрольные суммы тел отчётов без вывода содержимого. Закрыть временный
   переходный код, если для действующих записей он больше не нужен.
7. Обновить CHANGELOG, карту системы и статус с разделением: проверено локально,
   выпущено, подтверждено в живой системе. Недоступную проверку так и обозначить.

Откат: восстановление C по карте только для тех же телефонов/H и неизменённых
после миграции строк. Старый код не откатывать вслепую поверх новых данных;
обратный порядок публикации и восстановления предусмотреть заранее.
Миграция D1 не нужна автоматически: сначала использовать существующие поля.
Если без изменения схемы нельзя, включить обоснование и порядок в конкретный
план выпуска; не добавлять новые поля «на всякий случай».

Проверять пакетами на вымышленных данных, не тестовыми семьями в production.

| Сценарий | Что должно получиться |
|---|---|

## Уточнение пользователя: зачем нормализовать raw и какую форму выбрать

Актуальное направление от 23.10.2026 заменяет прежние обсуждения «только
исследовать» и «всегда оставлять исходное имя воспитателя».

Пользователь вспомнил исходную цель: автоматически удалять нужный блок при
выписке, а также заранее добавлять инициал, чтобы поступление нового тёзки
не требовало ручной переработки старого отчёта. Это нужно сохранить.

### Окончательное разделение представлений для реализации

| Где | Какое имя показываем |
|---|---|
| REPORTS!C | Имя из регистрации без инициала; не переименовываем по словарю |
| REPORTS!D | Полная фамилия |
| Сырой заголовок, имя есть в NAME_VARIANTS | Предпочитаемая форма из первого столбца + нужное уточнение фамилии |
| Сырой заголовок, имени нет в NAME_VARIANTS | Исходная форма воспитателя + нужное уточнение фамилии, если ребёнок однозначно установлен |
| Родительский заголовок | Имя конкретного ребёнка из регистрации |
| Тело отчёта | Без глобальных замен имён и авторской формулировки |

Например, если первый столбец содержит «Саша», а группа включает Александр и
Александра: сырой текст получает «Саша Ба» и «Саша Бу»; родительские заголовки —
«Александр» и «Александра», если именно так записаны профили.
Если предпочтительной формы для имени нет, нельзя придумывать её по сходству.

Саша/Александр/Александра — общая группа вариантов для поиска; это не разрешение
смешивать мальчика и девочку или двух девочек. Сначала безопасно определить
ребёнка по авторскому заголовку и полной фамилии, затем оформить заголовок.
Значимые сведения исходного заголовка нельзя потерять до проверки владельца.
Готовый заголовок должен при повторном разборе вести к тому же ребёнку.
Если предпочитаемая форма и доступное уточнение фамилии этого не обеспечивают,
сохранить исходное различающее написание/выдать предупреждение, не угадывать.

### Что дополнительно проверить

- Первый столбец — предпочтение оформления, а не самостоятельный идентификатор
  ребёнка. Смена первого слова группы не меняет H, семью, доступ или владельца.
  Проверить реальные зависимости `getNameBaseKey_`/CANON_NAME_MAP и старых
  ownership-хешей от этого столбца, прежде чем считать такую смену безопасной.
- Слова в остальных столбцах остаются равноценными синонимами при поиске.
  Не вводить правило, что имя из первого столбца «больше подходит» одному ребёнку.
- При двух фамилиях на одну букву автоматически расширять уточнение, только
  если прежняя принадлежность подтверждена. Позднее поступление/выписка не
  должны превращать старый неоднозначный блок в новый однозначный по догадке.
- Удаление ребёнка должно находить его блок независимо от формы имени в raw,
  старого количества букв фамилии и зарегистрированного написания C.
- Проверить два родственника, несколько Саш, появление второго тёзки,
  смену предпочитаемой формы в словаре и последующую выписку.
- Убедиться, что родительский заголовок использует C, даже когда raw оформлен
  иначе, и что уведомления/история/прочитанность не воспринимают смену подписи
  как новый текст. Не менять имена внутри тела автоматической заменой.
