## Результат, которого хотим добиться

Пользователь быстро получает подтверждение регистрации/выписки. Фоновые задачи
не теряют незавершённые шаги. Получение списка профилей не меняет таблицу.
Два пути распределения используют один расчёт, сохраняя разные эффекты:
публикация может уведомлять, обслуживание справочника — нет.

Это ограниченный следующий этап, а не поручение переписать весь бот.
Луна выполняет A → B → C. A меняет межсервисный контракт: после локальной
реализации нужен короткий review Sol по checkpoint/повторам перед выпуском;
B и ограниченный C можно завершать по приведённым критериям. Перед переносом сетевых вызовов из блокировок и сменой
идентичности поступления — вернуться к Sol с результатами A–C и проектом D.
Не выдавать частичную защиту от гонки за полное решение.

## Неизменные условия

- Sheets хранит редактируемый REPORTS и raw-источники отчётов. Worker хранит
  сессии, чаты, очереди и состояния веб-интерфейса. Новую платформу не вводим.
- Сохранённые сессии, passkey-предложения и 72-часовой вход не менять.
- NAME_VARIANTS, различение Александр/Александра, инициалы, полные фамилии и
  владельцы raw-блоков работают по прежним правилам. Не очищать реестр владельцев.
- Мама и папа одного ребёнка остаются двумя контактами одного поступления.
- Ручное значение G важнее автоматического определения; DATABASE и контакты нужны.
- Имена внешних API и установленных trigger-функций сохранять. Новый GAS-файл
  включать в `.claspignore`; все серверные функции по-прежнему в общем GAS scope.
- Не применять stash целиком. Он содержит отдельные прототипы и небезопасный
  старый черновик входа. Работать с актуальным основным checkout.

## A. Закончить контракт фоновой выписки

**Приоритет первый: это исправление обнаруженного дефекта, не косметика.**

Файлы: `apps-script/medsi-bot/Медси бот.js`, при выделении — новый
`parent-lifecycle.js`; Worker `src/index.js`; `tutors/full-web.js` и transport
только для фонового статуса. Не менять алгоритм распределения и схему D1.

### A1. Идемпотентное продолжение по operationId

1. До удаления строк сохранить компактный checkpoint в Script Properties
   `PARENT_DELETION_PROGRESS_<operationId>`. Версия формата, телефон, ожидаемые
   parent/child, локальный admission-token, точные raw-targets и статусы шагов.
   Не сохранять тела отчётов, сообщений и весь roster. Не логировать содержимое.
2. Checkpoint создаётся под уже существующим ScriptLock; helper не берёт второй
   lock. Повтор той же операции читает запись, а не заново определяет старого
   ребёнка только по нынешней строке/номеру.
3. Перед удалением текущих строк проверить ожидаемую идентичность и сохранённый
   admission-token. Если там уже другое поступление, остановить destructive-часть
   с `RECORD_CHANGED`, не удалять нового ребёнка. Не считать разные поколения
   одинаковыми только из-за совпадения имени и телефона.
4. Если строка уже отсутствует, продолжить незаконченные шаги по checkpoint.
   Raw-cleanup пересчитывать из сохранённых targets и СЕЙЧАС активных детей;
   прежний диапазон или текст отчёта не писать обратно. Текущие ownership-guards
   и сравнение исходного raw перед записью сохранить.
5. Если старая уже ожидающая задача не имеет checkpoint, безопасно восстановить
   targets из совпадающего прежнего lifecycle snapshot. Если доказательств нет,
   вернуть явный незавершённый результат для разбора; не угадывать ребёнка.

### A2. Что означает завершение

| Результат GAS | Действие Worker |
|---|---|
| Критические шаги завершены; вторичные либо сделаны, либо сохранены в отдельной durable-очереди | `completed` |
| Строка/raw-очистка ещё не закончены или вторичный шаг лишь упал без сохранённого повтора | `retry`, затем видимый `failed` после прежнего лимита |
| Та же операция ещё выполняется | Не объявлять завершённой; повторять с прежним operationId |
| Обнаружено другое поступление | Остановить старое удаление и показать конфликт, не чистить новый профиль |

В новом ответе явно возвращать `coreComplete`, `cleanupComplete`, `pendingSteps`.
`ok:true` означает корректно обработанный запрос, не обязательно завершённую
работу. Старый `{ok:true,cleanupComplete:false}` Worker тоже обязан считать
незавершённым. Простого условия на один флаг недостаточно без A1: строка уже
могла исчезнуть и повтор потеряет исходные targets.

Критические шаги: закрытый доступ, удалённая старая строка REPORTS и безопасно
завершённая очистка её raw-блоков. Уже существующую S3 purge queue использовать
повторно. Контакты/медиа можно дочищать отдельно только при сохранённом намерении;
отложенный шаг адресовать прежнему ресурсу/поколению, не новому контакту по номеру.
Checkpoint нельзя выбрасывать по TTL, пока остаётся незавершённая работа;
retention успешных записей согласовать с retention Worker deletion queue.

`failed` с незавершённой критической частью продолжает запрещать автоматическое
восстановление через reconcile и регистрацию на тот же номер. Добавить защищённый
повтор той же операции; не требовать нового идентификатора и не запускать всё
с начала. Уже completed-задача не удаляет новый профиль при повторе команды.
Не превращать техническую ошибку в незаметный постоянный запрет входа.

### A3. Видимость фона без ожидания пользователя

Сохранить быстрый accepted и скрытие карточки. operationId сохранять до отправки.
Использовать существующий `parentDeleteStatus` для активных задач: ограниченные
фоновые проверки, без polling всех телефонов. При открытии панели получать
небольшой список незавершённых/failed задач, чтобы ошибка не терялась при закрытии
браузера или на другом устройстве воспитателя. Failed показать коротко с кнопкой
повтора. Не возвращать доступ/карточку как активную только из-за сбоя очистки.
Потерянный ответ accepted проверять/повторять по прежнему operationId.

### Приёмка A

- Сбой после удаления строки, но до raw/contact cleanup → тот же operationId
  заканчивает работу; Worker не ставит premature completed.
- Задержка GAS/медиа не задерживает accepted и исчезновение карточки.
- Потерянный ACK/повтор worker execution не создаёт второе удаление.
- Новая регистрация через Worker с тем же телефоном не удаляется старым повтором:
  пока критическая очистка не закончена, она блокируется; после завершения старый
  operationId возвращает сохранённый итог без повторного D1-delete.
- Ошибка фона видна после перезагрузки панели; повтор адресует ту же операцию.
- Новую регистрацию/доступ родителей ради проверки не создавать и не сбрасывать.

Порядок совместимого выпуска: сначала Worker сохраняет запрет recreate при
незавершённом failed-delete, затем GAS с checkpoint и новыми полями, затем Worker,
который интерпретирует завершение и предоставляет безопасный retry, затем статус
в панели. До введения стабильной метки строки нельзя обещать, что ручное удаление
и создание абсолютно такой же строки в Sheets отличимо от прежней строки:
этот случай относится к D. Не скрывать его приёмочным тестом только с разными
именами. Выпуск — согласованная пачка, а не коммит на helper.

2. Выделить явный `fillMissingParentRelationships_`: заполняет только пустые G,

3. Новая регистрация заполняет свою G прямо при append. Уже существующие пустоты

5. Snapshot берёт строки одним чтением и передаёт их вычислителям; базовые столбцы

пустая G отображается и затем штатно заполняется; параллельная ручная правка
сохраняет приоритет. Ни схемы D1, ни авторизацию эта пачка не меняет.

## C. Общее вычисление двух распределителей

Файлы: новый `report-distribution.js`, два координатора в `Медси бот.js`,
`.claspignore`, `tests/report-pipeline-contract.test.cjs` и существующие fixtures.

Реализовано: чистое оформление `buildReportRowValues_`, общий чистый расчёт
парсинга/назначений одного kind в `computeReportKindPlan_` и отдельный чистый
`planRawReportOwnershipGuard_`. Оба координатора пользуются ими; внешние записи
остаются в явном commit.

Целевая граница вычисления:

```text
ReportInput = kind + rawText + roster + nameVariants + previousReports
              + admissionTokens + ownershipRecords
ReportPlan  = valuesByRow + resolutions + blockedRows + notes
              + proposedOwnershipWrites + sourceFingerprint + rosterFingerprint
```

Input загружается до расчёта. Compute не вызывает Sheets/Properties/HTTP и не
вставляет Date.now/UUID. Результат для одинакового input одинаковый.
Владельцы загружаются до расчёта; `planRawReportOwnershipGuard_` только возвращает
предложения для записи и не меняет Properties. Перед сохранением ownership и E/F
координаторы повторно сверяют исходный текст и roster. Маркер публикации истории
также записывается после успешной записи E/F. При несовпадении расчёт отменяется,
ошибка уходит обычному обработчику; следующий source edit/reconcile может повторить
работу. Между ручной правкой Sheets и записью нет общей транзакции, поэтому это
короткое проверяемое окно, а не атомарная фиксация с Sheets.

Побочные эффекты остаются в явных координаторах:

| Операция | Новая публикация | Maintenance |
|---|---|---|
| Вычислить назначения/оформить E или F | Да | Да, только выбранный kind |
| Применить допустимые ownership-записи и notes | Да | Да, без присвоения старого блока новому ребёнку |
| Создать событие публикации, менять её дату | Да | Нет |
| Запустить уведомление | По прежним правилам | Нет |
| Потерять предупреждение guard после успешного форматирования | Нет | Нет |

Перед commit сохранить roster-barrier; дополнительно сравнивать исходный raw
с тем, из которого считали plan. При изменении — отменить устаревший commit и
оставить запрос на пересчёт. Это уменьшает окно, но не объявляется транзакцией
с ручным редактором Sheets. Запись E/F только при изменившихся значениях допустима
как адресная оптимизация, без сдвига версии публикации/прочитанности.

Приёмка: существующие fixtures для обоих координаторов и permutations, NAME_VARIANTS,
двух родственников, пустоты, явных Александр/Александра, неизвестного/голого заголовка,
выписки тёзки и смены roster между расчётом и записью. Не создавать сотни похожих
тестов; расширить существующие содержательными сценариями. Сохранить различие
между новой публикацией и обслуживанием справочника.

## D. Дизайн Sol: поколения и доставка, затем короткие блокировки

Дизайн подготовлен 22.10.2026: [поколения, доставка отчётов и короткая фиксация](audit/2026-10-22-apps-script-generations-and-delivery-design.md).
В нём определены fence по `attemptId`, монотонная ревизия, порядок совместимого
выпуска и сценарии синтетической проверки. ID поступления в REPORTS и его
использование raw-owner опубликованы в Apps Script; D1 и общие границы блокировок
не менялись.
`childAdmissionId` хранится в скрытом `REPORTS!H`, не в новом листе или D1.
Apps Script объединяет только строки, которые уже совпадают по действующему
ключу `NAME_VARIANTS` + фамилия + гендерные признаки; удаление всех строк и
новая регистрация создают новый ID. Двух одновременных полных тёзок текущая
логика сама разделить не может. Реальную конфигурацию установленных триггеров
ещё нужно подтвердить.

**Не отдавать Луне как свободное поручение «убрать lock/добавить admissionId».**
Сначала сопоставить результаты A–C с этими обязательными решениями:

- Постоянный ID поступления ребёнка отличается от auth generation одного родителя.
  Несколько взрослых одного ребёнка разделяют поступление, но не auth-профиль.
- Проекция регистрации несёт attemptId и ожидаемое поколение. Устаревший полученный
  outbox не даёт права append/reconcile после отмены. Worker подтверждает фактический
  результат ACK. Между Sheets и D1 нет общей транзакции: нужны сохраняемая отметка
  применения и проверка поколения, а не ещё один GET до локального lock.
- Служебный ID хранится в `REPORTS!H`; при backfill совпадающие текущие строки
  группируются по тому же ключу, которым Apps Script уже распределяет отчёты.
  Если строки вручную размечены разными ID, код не объединяет их молча.
- Текущий отчёт несёт поколение профиля/поступления и монотонную ревизию коммита
  GAS. Worker принимает только актуальное поколение и более новую ревизию; тот же
  revision с тем же payload — повтор, с другим payload — конфликт. Date.now при
  HTTP-доставке не заменяет ревизию источника. Отдельно сохранить publicationId,
  чтобы перестановка roster не стала новой рассылкой и unread-событием.
- История, current reports, profile reconcile и deletion должны одинаково отвергать
  старое поколение. Старый снимок после выписки не должен оживить ни профиль,
  ни отчёт для вновь созданного профиля с тем же телефоном.
- Только после этого: короткий общий lock на фиксацию изменений Sheets/Properties;
  HTTP/Contacts/S3 вне него; отдельный сохраняемый claim/lease на долгую фоновую
  задачу. Схема load → compute → validate/commit → deliver → ACK. Занятость означает
  сохранённый повтор, не тихий skip и не 15 секунд ожидания интерфейса.
- UserLock нельзя считать независимым lock «отчётов» без проверки, от чьего имени
  исполняются web app и triggers. Реальный режим/инвентарь триггеров проверить
  технически, без данных семей, перед сменой области блокировок.

Нужные проверки D: revoke между fetch и apply outbox; delete/re-register того же
номера; старый сетевой пакет приходит после нового; сбой между записью и ACK;
ручное удаление строки сразу после проекции; два взрослых одного ребёнка.
Переход должен иметь совместимый backend → привязку существующих данных →
переключение писателей → строгий запрет старого формата. Никакого сброса сессий
или массовой переинтерпретации старых raw owners. Новые D1-миграции/столбцы
предлагать отдельно с конкретной схемой; в A–C они не требуются.

## E. Чистка после нового протокола

Составить реестр внешних API, callers и trigger entry points. Обёртки текущего
Worker не считать старой системой только из-за старого имени. Удалять лишь
доказанно ненужный путь; no-op заглушка старого установленного триггера может быть
полезнее удаления имени. Sheet-only read-state/import код кандидат на снятие
после подтверждения D1 cutover и отсутствия потребителей, без возврата удалённых
листов. Не менять разом API-карту и механизм авторизации.

**Статическая сверка 22.10.2026:** текущая родительская форма вызывает общий

## Ритм работы и выпуск

Одна осмысленная пачка A; затем B/C, если их можно закончить согласованно.
Не делать коммит на каждую функцию. По ходу — адресные тесты; один полный
`npm run verify` и `git diff --check` перед выпуском пачки, как требует AGENTS.
Не повторять успешные прогоны без изменения или найденного риска.
Проверять нужный workflow и реальный технический результат deployment;
публикация source не равна обновлению active web app.

На каждую пачку кратко записать: новый сценарий, изменённые файлы, проверки,
Git SHA, что выпущено и что осталось локально. CHANGELOG описывает поведение.
Timeweb, замер расхода D1 и passkey на устройстве остаются отложенными по просьбе
пользователя. Реальных детей не регистрировать/выписывать ради проверки.
